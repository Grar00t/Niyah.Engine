# Persistence and publication contracts

The tokenizer, shard, checkpoint, and cursor serialized formats and public C signatures are unchanged. Their save routines still permit intentional replacement, but now write in an exclusively created sibling staging directory and atomically replace the final directory entry only after checked flush and close. A failed write never deletes the previous destination. A save to a hard-link or symbolic-link alias replaces that directory entry, rather than truncating the aliased inode. This is safer than the former alias-following write behavior. Serialized reader validation remains unchanged; Windows path decoding is described below.

The prepare/shard and training CLIs instead use no-replace publication: Windows CreateHardLinkW or POSIX link from a fully written private staging artifact. Existing paths, including aliases, are never opened for writing. A failed existence/access probe does not grant write authority; the final exclusive link decides. A filesystem that cannot create same-filesystem hard links fails closed. The staging directory is created exclusively (0700 on POSIX; inherited directory ACL on Windows). Failed staging cleanup produces an IO failure and a diagnostic with the owned path. Cleanup never removes a final output. Partial prepare publication may therefore leave a complete tokenizer if shard publication fails; it never reports overall success.

These guarantees concern cooperating processes in an ordinary user-controlled local directory, not hostile directory replacement, concurrent arbitrary editing of published artifacts, or power-loss durability. No fsync/storage-barrier guarantee is claimed. The tokenizer, shard, checkpoint, cursor, and publication path APIs now require UTF-8 on Windows and convert strictly to wide Windows filesystem calls. ASCII callers remain compatible; native callers previously passing locale-specific ANSI bytes must convert their paths to UTF-8. No ambiguous ANSI fallback is attempted. CLI Windows arguments are converted from UTF-16 consistently. Persisted artifact bytes and versions are unchanged; POSIX path bytes are unchanged. Existing artifacts remain readable by supplying their actual filenames under this path encoding contract.

## Checkpoint/cursor completion protocol v1

`niyah-train` publishes checkpoint-path.pending first with exactly eight bytes `NIYAHPI1`. It reserves that checkpoint publication name without replacement. It stages both legacy-format artifacts, calculates checkpoint identity, binds the cursor to it, reads both through existing native readers, then exclusively publishes checkpoint and cursor. It rehashes the final files and publishes checkpoint-path.complete last. Completion is exactly 72 bytes: `NIYAHPR1`, raw checkpoint SHA-256 (32 bytes), raw cursor SHA-256 (32 bytes). The pending reservation is retained even after success, deliberately.

This is NOT atomic two-file publication. An interrupted attempt can leave zero, one, or two complete artifacts and a pending marker. It must not be automatically retried against the same names; choose new output paths. Failed attempts never delete final files or an unrelated contender's destination. Private temporary artifacts are cleaned after normal error returns; process termination can leave private staging directories, which this protocol does not automatically recover or remove.

The consumer enforcing the protocol is `niyah-train resume`. When either sidecar exists it checks exact metadata shape, checkpoint and cursor raw identities and cursor-to-checkpoint binding before accepting the pair. Missing completion with a pending reservation, malformed/stale metadata, trailing bytes, and mismatched identities fail closed. The normal tokenizer, dataset, cursor, optimizer and checkpoint checks still apply. Inference/evaluation and model-only fine-tuning consume a single checkpoint and do not assert pair completion.

For legacy compatibility, absence of BOTH metadata files permits the preexisting resume checks (dataset identity and checkpoint binding); stderr reports `pair_protocol=legacy_binding_only`. Existing valid step2100 and earlier pairs need no changes. Copying a new pair without BOTH metadata files is indistinguishable from a legacy pair; provenance-aware copies must retain both sidecars. Metadata is content consistency, not cryptographic authentication; removing all metadata or rewriting all files is outside this guarantee.

The writer retains both sidecars after success, but the reader also accepts a
valid `.complete` when `.pending` is absent. Thus a retained pending marker is
not by itself an incomplete-pair signal; completion validity decides acceptance.

## Verification

`niyah_publication_test` uses isolated temporary fixtures and a private test callback, not production environment variables. It tests all four native serializers, byte-compatible roundtrips, deterministic staged-write/publication/cleanup failures, concurrent contenders, hard-link and dot-path aliases, Windows sharing denial, all pair fault boundaries, actual resume acceptance/rejection, malformed and stale metadata, and legacy pairs. Test-only native training uses tiny random fixtures; it does not continue the user's model. CMake CLI fixture runs use unique output directories and preserve previous results.
