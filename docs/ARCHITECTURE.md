# Architecture

Niyah.Engine is organized around one primary invariant:

> **Training, persistence, evaluation, and inference operate on one canonical `NiyahModel` parameter layout.**

There is no required external model runtime behind generation, and there is no separate hidden model representation used only for training.

## System boundary

The native model core owns:

- model configuration and canonical parameter layout;
- tokenizer training, encode/decode, persistence, and identity;
- dataset shard construction, loading, geometry, and identity;
- deterministic dataset cursor state;
- Transformer forward execution;
- incremental KV-cache decode;
- causal language-model loss;
- response-masked supervised loss;
- explicit backward gradients;
- global gradient clipping;
- AdamW optimizer state and updates;
- checkpoint persistence and compatibility validation;
- read-only evaluation;
- sampling and autoregressive generation.

Application infrastructure such as RAG, databases, hosted APIs, agent orchestration, GUIs, and HTTP servers remains outside this boundary unless a separate application adds it.


## Canonical model representation

`NiyahModel` owns a validated configuration, a computed layout, a contiguous FP32 weight array, and a weight count.

Conceptually, the parameter order is:

```text
token_embedding [vocab, dim]
optional segment_embedding [segments, dim]
for each Transformer layer:
  attn_norm      [dim]
  wq             [dim, dim]
  wk             [kv_dim, dim]
  wv             [kv_dim, dim]
  wo             [dim, dim]
  ffn_norm       [dim]
  w_gate         [ffn, dim]
  w_up           [ffn, dim]
  w_down         [dim, ffn]
final_norm        [dim]
lm_head           [vocab, dim]   # separate only when embeddings are untied
```

Derived attention geometry:

```text
head_dim = embedding_dim / n_heads
kv_dim   = head_dim * n_kv_heads
```

### Model invariants

- invalid head/GQA geometry is rejected;
- size arithmetic is overflow-checked;
- tied embeddings reuse model storage rather than duplicating the LM head;
- initialization is deterministic for a fixed model seed;
- CPU FP32 is the reference numerical path;
- optional segment embeddings are a learned signal, not a security boundary.

## Transformer path

The full-sequence forward path is conceptually:

```text
token ids
  ↓
token embeddings
  ↓
optional segment embeddings
  ↓
N × Transformer layer
    ├─ RMSNorm
    ├─ RoPE
    ├─ causal grouped-query attention
    ├─ residual
    ├─ RMSNorm
    ├─ SwiGLU feed-forward
    └─ residual
  ↓
final RMSNorm
  ↓
LM head
  ↓
logits
```

### Grouped-query attention

The model supports `n_kv_heads <= n_heads`. Query heads map onto the smaller K/V head set according to validated GQA geometry.

### RoPE

Rotary positional encoding is applied inside the attention path. Runtime prompts are constructed with the BOS token before user prompt tokens so inference position semantics match the supervised training contract.

## Tokenizer

The tokenizer is native to Niyah.Engine.

### Base vocabulary

```text
0..255  raw byte tokens
256     BOS
257     EOS
258+    learned BPE merge tokens
```

The base vocabulary is therefore 258 tokens. The configured target vocabulary is an upper training target; the realized vocabulary depends on learned merges.

### Properties

- arbitrary input bytes are representable without an unknown-token fallback;
- UTF-8 is handled as bytes and can round-trip through encode/decode;
- BPE training/application is deterministic under the implemented contract;
- tokenizer persistence carries a stable SHA-256 identity;
- downstream checkpoint/dataset compatibility checks use tokenizer identity.

## Dataset architecture

Dataset state is split into **persisted content** and **sequencing state**.

### Dataset shard

`NiyahDatasetShard` stores tokenizer-bound token content and sample geometry. The versioned `NIYAHSRD` formats support current record/sample contracts, including response-objective boundaries where applicable.

Preparation supports:

- continuous text streams;
- blank-line record boundaries;
- supervised prompt/response records using explicit response delimiters;
- response-only objective masking while retaining prompt tokens as causal context.

Basic shifted causal samples have the form:

```text
input : t0 t1 t2 ... tN-1
target: t1 t2 t3 ... tN
```

### Dataset cursor

`NiyahDatasetCursor` tracks deterministic sample ordering/progress separately from model weights.

Persisted cursor state can bind to:

- sample count;
- ordered dataset collection identity;
- checkpoint identity;
- deterministic epoch/order position.

The checkpoint and cursor therefore form an explicit resumable-state pair without embedding sequencing state inside the model object.

## Training

`niyah-train` exposes:

```text
new
resume
```

### New training

```text
tokenizer + ordered shards
  ↓
model initialization
  ↓
AdamW initialization
  ↓
deterministic dataset cursor
  ↓
select sample
  ↓
forward + cross entropy
  ↓
backward
  ↓
accumulate gradients
  ↓
average + global L2 clip
  ↓
AdamW update
  ↓
repeat
  ↓
checkpoint save
  ↓
checkpoint identity
  ↓
cursor binding + save
```

The number of sample consumptions per optimizer update is:

```text
batch_size × accumulation_steps
```

This is deterministic sequential gradient accumulation, not a claim of vectorized tensor mini-batching.

### Response-masked supervision

For prepared supervised records, prompt tokens remain part of the forward causal context while direct objective supervision begins at the configured response boundary.

### Progress

Completed optimizer updates are emitted to stderr:

```text
update=I/N loss=L
```

The per-update value is training loss, not validation loss.

## Resume contract

Resume loads persisted state instead of silently initializing a new run:

```text
tokenizer
+ model checkpoint
+ dataset cursor
+ ordered shard collection
        ↓
validate tokenizer/checkpoint compatibility
validate dataset collection identity
validate sample count/cursor state
validate checkpoint binding
validate model/context compatibility
        ↓
continue optimizer updates
        ↓
write new checkpoint + new cursor
```

Resume inputs are not overwritten; output paths must be new paths.

## Checkpoint architecture

A checkpoint persists the state required by the current trainable lifecycle, including:

- canonical model configuration;
- canonical model weights;
- AdamW first moments;
- AdamW second moments;
- optimizer step;
- optimizer hyperparameters;
- tokenizer compatibility metadata in tokenizer-bound formats.

Persistence is versioned and validated before reconstructed state is published to callers.

A separately persisted dataset cursor completes the resume state.

## Evaluation

The native `niyah_evaluate()` primitive is read-only over caller-owned samples and reports:

```text
sample_count
token_count
mean_loss
perplexity = exp(mean_loss)
```

The current documented `main` CLI does not expose `niyah eval`; project evaluation has also been exercised through diagnostic helper binaries.

Evaluation metrics only become quality evidence when dataset provenance, tokenizer semantics, objective geometry, and held-out discipline are known.

See [EVALUATION.md](EVALUATION.md).

## Inference

`niyah run` performs:

```text
tok.bin + checkpoint
  ↓
load tokenizer
  ↓
load tokenizer-bound checkpoint
  ↓
encode BOS + prompt
  ↓
incremental KV-cache decode
  ↓
sampler
  ↓
decode selected tokens to bytes
```

Context capacity is validated before generation proceeds.

### Sampling

- `temperature=0`: deterministic greedy selection;
- positive temperature: seeded stochastic sampling under the implemented sampler contract.

## Diagnostic probe

`niyah_probe` is a standalone inspection tool that does not modify training behavior or sampler/generation semantics.

It can inspect:

- shard unigram/token statistics;
- prompt token IDs;
- top-k next-token logits/probabilities;
- selected-token decoded bytes;
- autoregressive KV-cache progression.

This makes generation failures inspectable without patching the core generation path merely to obtain visibility.

## CPU and CUDA

### CPU FP32

CPU FP32 is the project reference path.

### Optional CUDA

CUDA is enabled at configure time:

```sh
cmake -S . -B build-cuda \
  -DNIYAH_BUILD_TESTS=ON \
  -DNIYAH_ENABLE_CUDA=ON
cmake --build build-cuda --config Release
```

When available, the runtime can select:

```text
--backend cpu
--backend cuda
```

The existence of a CUDA path does not establish mixed-precision correctness, distributed training, production accelerator readiness, or CPU/CUDA bitwise equivalence.

## CI and failure boundaries

The repository `core-ci` workflow defines:

- Ubuntu Release configure/build/test;
- Windows Release configure/build/test;
- Ubuntu Debug ASan/UBSan configure/build/test.

Core code is compiled under the configured warning-as-error policy.

The implementation prefers explicit rejection over silent incompatible state. Validation boundaries include:

- model geometry;
- non-finite numerical states;
- tokenizer/shard compatibility;
- checkpoint structure/corruption checks;
- cursor/dataset/checkpoint identities;
- output-path collisions;
- context capacity;
- optimizer/configuration compatibility.

## Architectural non-goals

The model core does not require:

- external LLM runtimes;
- hosted model APIs;
- RAG/vector stores;
- relational/document databases;
- agent/tool orchestration frameworks;
- GUI shells;
- web serving infrastructure.

Those systems may be added around Niyah.Engine when an application establishes the requirement.
